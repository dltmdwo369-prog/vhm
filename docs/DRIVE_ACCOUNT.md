# 캘린더와 Drive 계정 분리 (2026-11-20)

캘린더는 기존 계정과 메모 잠금 키를 유지하고, 파일 저장용 Google Drive만 다른 계정으로 연결할 수 있습니다. Google OAuth 프로젝트·클라이언트 ID·리디렉션 주소는 변경하지 않았으며 기존 `calendar` / `drive.file` 범위만 사용합니다. Drive 연결에서 Calendar 권한이나 새 서버 접근을 요청하지 않습니다.

## 새 저장 계정 연결

1. 기존 캘린더 계정으로 로그인한 상태에서 **설정 → Drive 저장 계정**을 엽니다.
2. **저장용 Google 계정 이메일**을 입력하고 **저장용 Drive 연결**을 누릅니다. 작성 중인 메모는 먼저 저장하세요. Google 로그인으로 이동하면서 미저장 화면은 초기화됩니다.
3. Google 계정 선택창에서 입력한 저장용 계정으로 로그인하고 Drive 권한을 승인합니다.
4. 돌아온 설정 화면에서 캘린더와 Drive의 계정을 각각 확인합니다. Drive API가 반환한 이메일이 입력한 이메일과 일치해야 저장 기능이 활성화됩니다. `login_hint`만으로 계정을 신뢰하지 않습니다.

계정 이메일은 **이 브라우저의 캘린더 계정별 설정**으로 저장합니다. 공개 HTML/소스에 실제 저장 계정을 고정하지 않습니다. PC·태블릿마다 같은 저장용 이메일을 한 번씩 설정·로그인해야 합니다. 비밀번호·인증번호를 개발자에게 전달하지 않습니다.

아직 별도 계정을 선택하지 않은 기존 브라우저는 기존 Drive 연결을 유지합니다. 별도 계정을 선택한 뒤에는 토큰 만료·거부·로그아웃 시 예전 캘린더 계정의 Drive로 자동 저장 경로를 되돌리지 않습니다. 저장용 Drive에 다시 연결해야 합니다. Drive만 연결 해제해도 캘린더 연결은 유지됩니다. 전체 연결 해제는 모든 토큰을 지우고 서버 파일은 삭제하지 않습니다.

앱이 Google OAuth 테스트 상태라면 새 저장 계정도 해당 OAuth 프로젝트의 **테스트 사용자**에 등록되어 있어야 할 수 있습니다. ‘access_denied’ 또는 테스트 사용자 오류가 나오면 프로젝트 소유자가 Google 인증 플랫폼의 대상/테스트 사용자 설정을 확인하세요. 웹사이트 코드에서 이 승인을 대신하거나 우회하지 않습니다.

## 기존 자료 복사

계정 연결만으로 기존 Drive 자료가 자동 이전되지는 않습니다. 원본은 이전 계정에 그대로 남습니다.

1. **기존 Drive 자료를 새 계정으로 복사**를 펼칩니다.
2. 기존 계정의 읽기 연결이 없으면 **기존 Drive 읽기 연결**로 캘린더 계정에 해당하는 Drive를 승인합니다. 저장용 계정과 캘린더 계정은 유지됩니다. 기존 토큰에 Drive 권한이 남아 있으면 별도 읽기 로그인 없이 확인할 수 있습니다.
3. **복사 대상 확인**을 눌러 파일명·폴더·건너뜀 사유를 검토합니다. 이 단계는 파일을 읽기만 하며 업로드·삭제·공유 변경을 하지 않습니다.
4. 새 계정으로 복사한다는 확인란을 체크하고 **확인한 자료 복사**를 누릅니다. 복사 결과를 항목별로 확인하세요. ‘건너뜀/실패’는 이전 완료가 아닙니다.
5. 이후 상담메모에서 **태블릿·컴퓨터 동기화**를 실행합니다. 다른 기기도 새 저장용 Drive를 설정한 뒤 동기화하세요. 원래 캘린더 계정과 메모 잠금 암호를 그대로 사용합니다.

복사 범위는 앱이 만든 `방문건강관리 연계자료`, `방문건강관리 임시보관함` 폴더의 직접 포함 파일입니다. 상담 저장본·삭제 표식·질문 틀·개인 연계 목록·양식·암호화 이미지·지원되는 임시 파일을 복사합니다. 다른 Drive 폴더나 PHIS 기기 전용 대기 목록은 자동 이전하지 않습니다.

- 암호화된 상담·이미지는 복호화하거나 새 키로 바꾸지 않고 바이트 그대로 복사합니다. SHA-256으로 서버 재조회 내용 일치를 확인합니다.
- 원본의 수정시각을 복사 전후에 확인하고, 달라졌으면 중단합니다. 원본 Drive에는 쓰기·삭제·공유 변경을 하지 않습니다.
- 대상에 같은 이름/원본 ID의 파일이 있으면 내용이 같은 경우만 재사용합니다. 다르면 덮어쓰지 않습니다. 실패 후에는 새로 미리보기를 만들어 재시도할 수 있습니다. 충돌 파일은 내용을 확인하고 별도로 보존/정리해야 합니다.
- 삭제 표식을 먼저 복사하고, 삭제 대상으로 표시된 상담파일은 건너뜁니다. 삭제 기록을 빠뜨려 사용한 메모가 다시 올라오는 것을 방지합니다.
- 개인 연계 목록의 첨부 ID/Drive 링크는 검증된 새 파일 ID로 바꿉니다. 복사하지 못한 첨부가 있으면 목록 복사를 보류합니다. 새 목록이 이미 다른 내용으로 존재하면 자동 병합/덮어쓰기를 하지 않습니다.
- Calendar에 저장된 기존 이미지 ID는 수정하지 않습니다. 검증된 복사본의 원본 ID 속성으로 새 파일을 찾습니다. 복사 전 파일은 기존 계정의 읽기 연결이 유효하면 원본을 읽을 수 있습니다. 기존 계정에서 수정·삭제하는 경로로 쓰지 않습니다.
- **파일당 20MB 초과, Google 문서 형식, 하위 폴더는 개별 이전이 필요**합니다. 임시보관함의 만료 파일은 건너뛰고, 복사한 파일도 원래 만료시각을 유지합니다. 원본 파일이 기존 계정에 남으므로 기존 계정의 용량을 자동으로 비우지는 않습니다.
- 복사 도중에는 이 화면에서 계정 변경·로그아웃을 제한하고 연결 유지의 자동 페이지 이동도 미룹니다. 페이지를 닫거나 토큰이 만료되면 일부만 복사되었을 수 있으므로 결과 확인 후 다시 미리보기하세요. 기관 간 권한 체계를 제공하는 서버 작업은 아닙니다.

## 구현·보안

- Calendar 토큰은 기존 `vhm-token`, 새 Drive 토큰은 별도 `vhm-drive-token-v1`, 필요할 때 승인한 원본 읽기 토큰은 `vhm-drive-source-v1`에 각각 sessionStorage로 보관합니다. 토큰을 localStorage·URL 설정·로그에 남기지 않습니다. 계정 선택/분리 설정만 localStorage에 남습니다.
- OAuth nonce/응답 만료시간, Calendar 소유 계정, Drive `about.user.emailAddress`를 확인합니다. Drive-only 콜백이 Calendar 토큰을 대체하지 않습니다. 미검증/만료 토큰으로 쓰지 않습니다.
- `src/gcal-api.js`의 Calendar/Drive/Drive 업로드 URL을 구분하여 올바른 토큰을 사용합니다. 보관함의 직접 요청도 같은 Drive 토큰을 사용합니다. Drive 401은 Calendar 로그인/키를 지우지 않습니다.
- 기존 업무시간 연결 유지에서는 만료가 가까운 Calendar 또는 Drive를 해당 계정으로 갱신하며 이전 화면으로 돌아옵니다. Drive 자동 연결 실패가 Calendar 토큰을 교체하지 않습니다. 원본 읽기 연결이 만료되면 필요할 때 수동 재승인합니다.
- 원본·대상 파일 ID를 혼동하지 않도록 계정 변경 시 Drive 폴더/파일 캐시를 비웁니다. 이전 계정으로의 자동 쓰기 fallback은 없습니다. 기존 ID의 읽기 fallback은 원본 읽기 연결이 있는 경우에만 사용합니다.
- 소스 JSON의 모르는 필드는 보존하면서 첨부 참조만 바꾸고, DOM에는 파일명/계정 정보를 textContent 또는 HTML escaping으로 표시합니다.

## 검증 범위

가짜 Google 계정 두 개와 가상 파일만 사용합니다. Calendar 유지, Drive-only OAuth, 잘못 선택한 계정 거부, 토큰 격리/만료/연결 해제, 계정별 설정, 암호화 키/내용 보존, 원본 읽기/무변경, 복사 검증·충돌·중복·실패 후 재시도, 삭제 표식·첨부 참조·보관함·연결 유지·모바일을 검사합니다. 실제 사용자 계정 로그인·기관 승인·파일 이전은 사용자가 승인한 후 사이트에서 수행해야 하며 개발자가 대신 실행하지 않았습니다.
