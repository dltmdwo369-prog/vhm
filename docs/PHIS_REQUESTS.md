# PHIS 기록 요청 — 기기 내 준비 기능 (2026-11-17)

현재 버전은 PHIS에 접속하거나 기록하지 않습니다. Power Automate Desktop·로컬 RPA·보안망 전송 경로·PHIS 계정 저장·로그인 자동화는 없습니다. 실행·처리기 재시도·완료 처리는 비활성화되어 있습니다.

## 사용 방법과 저장 범위

1. 일정 탭에서 기존 Google 계정에 연결하고 메모 잠금을 풉니다.
2. 상담메모를 저장1·저장2…로 저장한 뒤, 해당 저장본의 **PHIS 기록 요청**을 누릅니다. 작성 중인 미저장 문장은 요청하지 않습니다.
3. 미리보기에서 저장된 원문을 확인합니다. 기존 저장 형식에는 구조화된 대상자 실명·전체 생년월일·상담일자가 없으므로, 없는 정보는 빈칸입니다. 문장·출생연도·저장시각으로 추측하지 않습니다. 확인한 정보만 보완하고 검토 체크 후 확정합니다.
4. **PHIS 기록 관리**에서 대상자·상담일자·상태로 찾고 상세 검토, 취소, 검토 후 재요청을 합니다. 여러 요청을 선택해 준비할 수 있지만, 준비해도 **요청 대기**이며 전송되지 않습니다. 선택 개수와 선택 해제를 제공합니다.
5. 필수 정보 누락·가려진 이름·원본 변경/부재·취소 상태는 처리 준비에서 제외합니다. 변경된 원문은 새 저장본으로 저장한 후 새 요청으로 검토합니다. 취소/검토 요청의 재요청은 같은 ID를 사용합니다.

**상담메모 Drive 동기화와 PHIS 요청은 별개입니다.** 요청은 현재 브라우저·기기에만 보관되며 태블릿에서 만든 요청이 PC에 나타나지 않습니다. 기존 상담메모는 기존 동기화 경로를 그대로 사용할 수 있습니다. 브라우저 자료 삭제·기기 고장 시 PHIS 요청은 복구할 수 없습니다. 현재 버전에는 PHIS 요청 내보내기/가져오기·원격 백업이 없습니다. 보관 기간·삭제·백업 정책은 기관 승인 후 별도 구현해야 합니다.

## 개인정보와 권한

- 기존 Google 로그인 + AES-GCM 메모 잠금 키를 재사용합니다. OAuth 프로젝트·클라이언트 ID·범위는 변경하지 않습니다. 신규 서버·DB 서비스·분석 스크립트·외부 전송은 추가하지 않습니다.
- Google 주 캘린더의 계정 이메일과 잠금 키 지문의 SHA-256 조합으로 요청 소유 범위를 구분합니다. 이메일을 확인할 수 없으면 요청을 만들지 않습니다. 기존 메모의 키 지문 범위로 원본을 조회합니다.
- IndexedDB `vhm-phis-requests-v1` / `jobs`에 `vhm-phis1:` AES-GCM 암호문을 저장합니다. 평문 봉투에는 요청 ID·해시 소유범위·원본 UUID·revision·암호문만 있습니다. 원본 ID/해시 등의 기기 메타데이터는 암호화되지 않습니다.
- 목록은 이름·생년월일을 가립니다. 상세는 연결·잠금 해제 상태에서만 보여줍니다. 요청 원문을 콘솔·일반 오류 로그·채널 메시지에 쓰지 않습니다. DOM은 `textContent`/`value`로 렌더링합니다.
- 잠금/로그아웃 시 복호화 목록·모달·검색조건을 지웁니다. 접근 상실은 포커스 복귀/주기 확인으로도 처리합니다. 기능 숨김은 권한 부여 수단이 아닙니다.
- 정적 웹 앱에는 기관별 역할·담당 대상자 범위·공식 감사 권한 서버가 없습니다. 현재 보호는 본인 계정과 잠금 키 기준이며, 기관 권한 체계나 악성 확장 프로그램/손상된 브라우저에 대한 보안 경계가 아닙니다. **실제 개인정보를 사용하기 전에 기관이 이 기기 저장 방식을 승인해야 합니다.**

## 데이터와 정합성

- 스키마1: `type=phis-record-request`, 고유 `id`, `sourceId`, `sourceFingerprint`, `ownerScope`, `cryptoScope`, `requestedAt`, `updatedAt`, `status`, `attempts`, `startedAt`, `finishedAt`, `error`, `preparedAt`, `revision`, `snapshot`, `review`, `history`.
- 요청 ID는 계정/키 소유범위+원본 UUID의 결정적 SHA-256입니다. 원본별 유일 인덱스 `[scope,sourceId]`와 IndexedDB readwrite 트랜잭션으로 같은 기기의 중복 생성/다중 창 갱신을 방지합니다. revision 비교 후 갱신하여 이전 상세 창이 새 변경을 덮어쓰지 못합니다.
- 요청 시점 `snapshot`에는 원문·원문 SHA-256·확인정보·정보 출처·캡처/원본 생성시각을 담습니다. 이후 보완은 `review`에 별도로 보존하고 원문 스냅샷/상담 원본을 수정하지 않습니다. 원본 암호문의 SHA-256 차이로 변경을 감지합니다. 원본이 없어져도 요청 스냅샷을 보존합니다. 동일 내용의 재암호화도 보수적으로 변경으로 분류됩니다.
- 봉투와 복호화된 ID/소유범위/원본/revision/키 지문, 원문 해시를 대조합니다. 읽지 못한 자료는 건수만 알리고 삭제/초기화하지 않습니다.
- BroadcastChannel은 내용 없는 갱신 알림만 보냅니다. 상태 결과나 성공 증거를 받는 채널이 아닙니다.
- 이력에는 사용자 로컬 요청/취소/검토/준비를 기록합니다. 브라우저 시계·클라이언트 이력이므로 서명된 기관 감사 로그가 아닙니다. 기기간 전역 중복 실행 방지는 향후 내부 처리기 책임입니다.

| 저장 상태 | 현재 허용 동작 |
| --- | --- |
| 요청 대기 (`pending`) | 검토 보완, 검토 필요 표시, 취소, 조건 충족 시 준비 표시 |
| 검토 필요 (`review`) | 검토 보완/재요청, 취소 |
| 요청 취소 (`cancelled`) | 원본 일치 확인 후 담당자가 재요청 |
| 처리 중·입력 완료·입력 실패 | 현재 생성/변경 불가. 외부 주입된 값도 검증된 결과로 인정하지 않고 검토 필요로 표시 |

준비 표시는 상태를 바꾸거나 시도 횟수를 올리지 않습니다. 연결 상태·승인 상태를 클라이언트 인자로 전달해도 실행/완료/실패/재시도를 허용하지 않습니다. 실패 작업의 오류 상세 표시 구조는 있지만 현재 실제 실패 결과 수신·재시도는 없습니다.

## 향후 승인된 내부 처리기 계약 — 설계만 제공

아래는 구현된 API가 아닙니다. URL·통신·자격증명·좌표·선택자를 정의하거나 배포하지 않았습니다.

| 논리 작업 | 승인 후 필요한 입력과 검증 |
| --- | --- |
| 승인 작업 조회 | 기관 사용자·역할·허용 대상자·실행 환경 인증, 명시적 승인 버전, 최소 데이터, 전송/보관 정책 |
| 작업 점유/시작 | canonical job ID + snapshot hash + expected revision, 서버 원자적 lease/fencing token, 중복 실행 차단, 시작 시각/시도 횟수/감사 이력 |
| 결과 보고 | 인증된 내부 처리기 식별, lease/시도 ID, PHIS 기록 식별자, 저장 후 재조회로 일치 확인한 근거, 검증 시각, 변조 방지/재전송 방지 |
| 완료 확정 | 브라우저의 success=true를 신뢰하지 않고 승인된 검증자가 대상자·상담일자·원문 해시와 실제 저장 근거를 확인한 후 원자적 완료 전이 |
| 실패/재시도 | 비식별 오류 코드, 민감정보 최소화, 재시도 가능 분류, 담당자 재승인, 이전 시도의 저장 여부 확인(불명확하면 자동 재입력 금지) |
| 취소 | 시작 전 취소와 실행 중 중지 요청을 구분, 이미 저장된 기록을 취소로 지우지 않음 |

PHIS 로그인은 사용자가 직접 수행합니다. 기관에서 실제 화면·대상자 검색의 정확 일치 기준·방문서비스/기타사항 필드·저장 확인 절차를 확인한 뒤 자동화를 작성해야 합니다. 동명이인/생년월일 불일치/여러 결과/원문 길이 초과/저장 결과 불명확 시 검토 중단이 필요합니다. 자동 입력 후에도 연계서비스 추가·세부 상담·기록 보완은 담당자 업무입니다.

## 보안 담당자 확인 사항

기관의 개인정보 처리 근거와 Google Drive/브라우저 저장 허용 범위, 관리 기기/잠금 키 정책, 역할·대상자 접근 범위, 보관/삭제/백업/감사 기간, 보안망 내부 승인 전달 경로, RPA 실행 승인·계정·실행 환경 검증, PHIS 저장 증거와 중복 실행/실패 재처리 정책을 먼저 확정해야 합니다. 외부 웹사이트와 보안망 사이의 직접 통신을 기본 전제로 삼지 않습니다.
