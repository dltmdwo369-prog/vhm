# 강서구 연계 안내 운영·개발 안내

## 자료와 의미

`data/public-referrals.json`은 사용자가 제공한 `vhm-link-research-2026-11-15.zip`의 공개기관 조사자료다. 버전은 `datasetId`, 확인일은 `checkedAt`에 있다. 현재 69건이며 `consultable` 48건, `needs_contact` 21건이다. 화면 수치는 배열에서 계산한다. ‘상담 및 연계 가능’은 공식 안내 또는 상담 경로가 조사됐다는 분류이며 현재 접수·잔여예산·수급 자격 확정이 아니다. 연락처와 정책 세부사항은 첨부 조사자료를 반영했으며, 개발 환경의 외부 공식 사이트 접근 제한 때문에 이번 구현에서 원문을 독립 재검증하지 못했다.

서울시 건강동행서비스의 대상 조건에 ‘1인가구 원칙, 다인가구 중 실질적 돌봄 부재자도 해당 가능’을 사용자 작업 요청에 따라 보완했다. 원본의 요금(2026년 시간당 6,000원)·공식 URL 등은 유지했다. 해당 항목 `implementationNotes`에 보완 근거와 재검증 한계를 기록했다. 그 외 사업 자격·연락처·URL을 추측해 보완하지 않았다.

빈 서류·근거 발행일·대상 연령 등은 상세에서 미확인으로 표시한다. `forms`에 있는 서식 **게시 페이지**는 다운로드 파일로 위장하지 않는다. 직접 PDF/HWP 링크를 새로 만들지 않았다. 제목이 없는 공식 안내는 ‘제목 미확인’을 표시한다.

2026년 강서구 일상돌봄은 대기 신청만 가능, 이동푸드마켓은 미운영(조사 JSON에 독립 서비스가 없어 공통 안내만 표시), 그냥드림은 신규 운영 안내로 표시한다. 개안·무릎 수술은 사전 신청/지원결정 조건을 상세에서 확인한다. 주택바우처는 수급가구 제외를 표시하고 기초수급·의료급여 자격 필터의 후보에서 제외한다. ‘대기/배정 여부 확인’은 대기 접수가 확정됐다는 뜻이 아니므로 ‘대기 신청만 가능’과 구분한다.

## 화면

- 요구 체크 → 추천: 메모리에서만 일치도를 계산한다. 기존 개인 요구 ID를 라벨로 해석해 공개자료의 라벨과 매칭한다. 없는 공개 요구는 임시 체크 항목으로 표시하며 개인 분류를 자동 수정하지 않는다. ‘만성질환 관리’만 기존 만성질환 항목의 알려진 별칭으로 처리한다. 의미를 임의로 추론하는 자동 매핑은 하지 않는다.
- 서비스 목록: 공개 상담자료와 개인 목록을 함께 검색한다. 분야·경제 자격·의뢰 방식·접수상태·출처 필터를 제공하고 12건씩 더 보기로 표시한다. ‘일반 차상위’를 ‘차상위본인부담경감’으로 취급하지 않는다. 필터는 자격 판정이 아니며 상세 조건을 항상 확인한다.
- 담당기관 확인 필요: 미검증 공개자료는 별도 검색한다. 조건에 맞는 것처럼 기본 추천하지 않는다. 같은 공개사업을 개인 목록으로 가져와도 확인 필요 분류를 유지한다.
- 상세: 조건·제외/중복·접수·연락처·절차·사전승인·서류·공식 근거·확인일·양식 상태를 표시한다. 의뢰코드 ①~④는 복지사업 신청 경로이며 일반 의료기관 진료의뢰서와 다를 수 있다.
- 개인 확인 기록: 운영 여부·강서구 적용 여부·담당부서·추천서·최근 확인일·근거·기관 메모를 개인 Drive의 `catalogReviews`에 저장한다. 기록이 추가됐다는 이유로 공개 확인 상태를 자동 승격하지 않는다. 대상자 정보를 적지 않는다.

## 개인 Drive 보호와 스키마

공개자료는 빌드에 인라인 내장돼 로그인·Drive 권한 없이 읽을 수 있다. 공개자료 열람 또는 개인 목록 읽기만으로 Drive 폴더·목록을 만들거나 수정하지 않는다. 로그인 후 Drive 권한이 이미 있으면 기존 개인 목록을 읽을 수 있으나 자동 저장은 하지 않는다. 새 파일은 개인 자료를 명시적으로 저장할 때만 생성한다.

구형 `schema:1`은 메모리에서 `schema:2`로 마이그레이션한다. 최상위·분류·항목·서비스·양식의 알 수 없는 필드를 JSON 형태로 유지하며 이미 높은 스키마 번호도 낮추지 않는다. 기존 ID, 사용자 분류, 첨부파일 ID는 보존한다. UI 호환 필드(`org`, `conditions`, `apply`, `memo`)를 공개 데이터의 대응 필드에서 보완하지만 원래 메타데이터를 삭제하지 않는다. 악성 URL은 실행 링크로 사용하지 않는다.

공개자료는 `catalogId`와 `catalogVersion`으로 개인 복사본의 출처를 남긴다. 같은 catalogId 또는 정확한 서비스명+기관명 조합이면 중복으로 보고 개인 수정 내용을 우선한다. 유사한 이름이라는 이유로 서로 다른 기관을 합치지 않는다. 이미 개인화된 복사본을 새 공개판으로 자동 갱신하지 않는다.

## 공개자료 선택 병합

1. 개인 목록을 불러오고 ‘가져오기·백업’에서 공개자료를 선택한다.
2. 최신 원격본으로 추가 건수·중복·새 요구 라벨을 미리 본다. 이 단계는 읽기만 한다.
3. 변경 전 백업을 다운로드한다. 기존 원격 JSON이 있으면 마이그레이션 전 원본을 백업한다. 브라우저 다운로드 저장을 직접 확인하고 확인란을 선택한다.
4. 기존 분류에 없는 요구 라벨을 표시한다. 사용자 동의가 있어야 ‘공개자료 추가 요구’ 분류를 추가한다. 기존 항목 ID를 우선 재사용한다.
5. 명시적 병합 확인 후 최신 원격 수정시각·데이터를 다시 비교한다. 바뀌었으면 중단하고 최신본을 다시 불러온다.
6. 저장 직전 메타데이터를 확인하고 `If-Match` ETag 조건부 PATCH를 사용한다. 412/삭제/수정시각 변경은 충돌로 처리하며 강제 덮어쓰기하지 않는다. ETag가 노출되지 않으면 안전하게 저장을 중단하고 오류를 표시한다. 이 헤더의 실제 Google 계정 동작은 미검증이다.

Drive는 파일명 유일성을 보장하지 않아 첫 생성의 원자적 유일성은 보장할 수 없다. 같은 이름의 폴더/목록이 여러 개 발견되면 임의 선택·삭제·통합 없이 중단한다. 기존 파일에 대한 동시 수정은 조건부 저장으로 보호한다. 중복 파일이 생겼다면 관리자가 원본을 각각 백업한 후 검토해야 한다.

## 백업·복원과 되돌리기

가져오기 전 백업은 원본 목록과 알려지지 않은 필드를 포함한다. ‘백업 파일로 바꾸기’는 사용자 확인 후 수행하고 현재 개인 목록도 다운로드한 뒤 복원한다. 원격 수정 충돌이 있으면 복원을 중단한다. 양식 파일 자체는 백업 JSON에 포함되지 않으며 Drive 파일 ID 연결만 유지된다. 백업 JSON은 타인에게 공유하지 않는다.

사이트 롤백은 이전 사이트 커밋을 별도 revert 커밋으로 되돌려 배포한다. Git 히스토리 강제 변경은 하지 않는다. 구버전 UI는 신규 메타데이터를 저장 시 버릴 수 있으므로, 사이트 롤백 후 개인 목록을 편집하기 전에 백업을 확보한다. 데이터 롤백은 새 버전의 복원 기능으로 원본 백업을 복원하는 것이 우선이다. 사이트 롤백 자체로 Drive 데이터를 자동 변경하지 않는다.

## 개인정보와 보안

요구 체크·필터·검색어는 저장/전송하지 않으며 메인 탭을 떠나면 초기화한다. 연결 해제 시 개인 데이터·요구 체크·병합 계획·확인 창을 비운다. Google OAuth 설정·권한, Calendar 연동, AES-GCM 메모 암호화는 유지한다. 연계자료 읽기/쓰기 부분만 수정했다. 신규 서버·DB·추적기·외부 API 호출은 추가하지 않았다. 외부 URL은 HTTP(S) 스킴과 자격정보 포함 여부를 검증하고 `noopener noreferrer`로 열린다. 기관·양식·메모를 HTML로 삽입할 때 이스케이프한다.

## 세부 요구 체크 확장

`data/refined-needs.json`에 11개 분야·44개 세부 상담 요구를 정의했다. 의료비·수술비, 치과·구강, 눈·귀, 질환·복약, 관절·재활·보조기기, 일상생활·퇴원 돌봄, 식사·영양, 기억력·마음건강, 독거·안전, 주거·냉난방, 이동·기관 연결·생계로 나눈다. 분야를 접고 펼칠 수 있으며 선택 개수가 표시된다. 기존·직접 관리 요구 항목도 같은 분야 메뉴에 통합하고 불명확한 항목은 기타에 표시한다.

세부 항목은 스크리닝 진단이나 사업 지원 범위를 새로 확정하는 정보가 아니라 상담 연결을 위한 태그다. 공개 서비스는 명시한 serviceIds에만 연결한다. 백내장 수술을 골랐다고 보청기 지원이 추천되거나, 장애인 치과 후원을 골랐다고 노인틀니 보험급여가 같은 지원으로 추천되지 않는다. 확인 필요 사업은 활성 추천과 분리된 확인 필요 영역에서만 볼 수 있다.

catalogId를 가진 개인 복사본도 같은 세부 연결을 쓴다. 사용자가 만든 일반 개인 서비스는 기존 포괄 요구 라벨(parents)과 연결하여 기존 서비스를 누락하지 않으며, 포괄 연결인 만큼 실제 세부 지원내용은 다시 확인하도록 안내한다. 한 세부 요구가 여러 포괄 라벨에 대응해도 같은 요구를 중복 집계하지 않는다.

세부 요구 및 펼침 상태는 화면 메모리에만 있고 기존 Drive 분류·ID·서비스·공개 카탈로그를 자동 수정하지 않는다. 초기화·탭 이탈·연결 해제 시 선택 요구가 지워진다. 새 세부 항목을 관리할 때는 JSON의 고유 ID·연결 서비스·부모 라벨을 검토하고 관련 모델·브라우저 테스트를 실행한다.

세분화 반영 후 검증: npm test 239개 PASS(실패 0), 기존 화면 반응형 4개 폭 통과. 공개 카탈로그 테스트 28개 안에 세부 요구·개인 포괄 연결·미확인 분리 및 같은 4개 폭 검증을 포함한다. 반복 빌드·루트/사이트 HTML 일치, 공개 조사자료·Drive/OAuth/암호화/상담 메모 소스 무변경도 확인했다.

## 요구 메뉴 통합

‘대상자 요구 체크’에서는 기존·직접 관리 요구를 별도 영역으로 나누지 않고 새 분야 메뉴에 함께 표시한다. 알려진 기존 라벨은 의료비·구강·눈/귀·질환·재활·돌봄·영양·마음건강·안전·주거·이동/생계 중 해당 분야로 배치한다. 분류를 특정하기 어려운 포괄 요구와 새 사용자 항목은 ‘기타’로 모은다. 정확한 라벨 매핑을 사용하며 사용자 분류명만 보고 내용을 추정하지 않는다.

이는 화면상의 배치 변경이다. 개인 Drive에 저장된 분류·요구 ID·서비스 연결은 재분류하거나 덮어쓰지 않는다. 같은 정규화 라벨이 여러 사용자 분류에 있거나 세부 요구와 정확히 같으면 화면에는 한 번 표시하고 체크/해제 시 원래 ID들을 모두 연결한다. 결과에서는 같은 라벨을 중복 집계하지 않는다. ‘요구 항목’ 편집 화면에서 사용자가 저장한 원본 분류는 계속 관리할 수 있다.

분야·항목 수와 선택 수는 통합 결과로 계산한다. 상세 요구 44개 외에 보존된 기존 요구와 사용자 정의 항목이 포함되므로 화면의 총 항목 수는 계정에 따라 달라진다.

메뉴 통합 후 최종 검증: 자동 테스트 246개 PASS, 실패 0; 기존 화면 반응형 4개 폭 통과. 초기 검증의 숨겨진 편집창 체크박스 선택 범위를 수정한 뒤 전체 재실행에서 통과했다. 빌드 재현성·루트/사이트 HTML 동일성·Drive 및 OAuth 소스 무변경을 확인했다.
